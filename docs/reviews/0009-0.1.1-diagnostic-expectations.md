`7a6ad32133cf52ba200ecb358d9c2723a9fcc052`. This dossier supplies bounded test

## Evidence and use

The source review is the local `agsdl-0.1.0-2026-09-07` dossier in
`/Users/oscarlahaie/.codex/reviews/`. Its `reproduce-deletions.py` starts from
[general-purpose-system.json](../../examples/0.1.0/general-purpose-system.json),

The 24 differences in `deletion-differences.json` reproduce exactly on the base
above. Every differing request still has the same verdict in both readers:
D fails for the two root cases; otherwise D passes and the requested G/R fails.
The differences concern Findings and Checks, not acceptance of these documents.

The [case ledger](0009-0.1.1-diagnostic-expectations.json) records all 24 exact
deletion pointers, operations, groups, source hashes and observed deltas. Its
deltas are evidence, not expected output. Neither reader nor the comparator is
an oracle. It deliberately contains no replacement full-report oracle.

To reproduce an individual case, parse the example, delete only the member at
the listed pointer, encode as UTF-8 JSON, and request the listed operation with
an empty annex map. Each deletion is a minimal mutation witness, not a claim
that the whole example is the smallest possible document. The first listed
case in each group is its representative. Preserve the other records: they
exercise the requirement to continue independent checks. Baseline bytes and
script hashes are in the ledger; scripts executed locally must use a temporary
copy with the checkout and output paths adapted, leaving the source intact.

Reader lots can assert the determined obligations below directly. For partially
determined groups, assert the common obligations and keep the named unresolved
diagnostic choice out of exact oracle tests. A maintenance implementation
convention must not be described as a new normative requirement. Any conceptual
resolution needs the separate proposal process before normative adoption.

## Unicode ordering: deferred 0.2.0 decision

`reproduce-unicode-order.py` requests inspect of primary bytes `{}` with two
annex map keys U+E000 and U+10000, each containing `{}`. It reproduces:

| Producer | InputRecord id order after primary |
| --- | --- |
| Python | `annex/\uE000`, `annex/\U00010000` |
| JavaScript | `annex/\U00010000`, `annex/\uE000` |

Scalar-value order puts U+E000 first. UTF-16 code-unit order puts U+10000 first
because its first surrogate is U+D800. These are explanations of the observed
implementations, not competing semantic oracles. The current comparator accepts
Python and rejects JavaScript with `input order/hash/boundary mismatch`.

[Reports](../../spec/reports.md) says Inputs are "sorted primary then annex id",
required-annex D Results are sorted by id, and Checks sort lexicographically with
locations by pointer text or byte value. [Serialization](../../spec/serialization.md)
defines string equality over decoded Unicode scalar sequences and rejects invalid
scalars. Equality does not specify an ordering relation. No published clause
selects scalar order, UTF-16 order or another collation for these report sorts.

Therefore this witness proves a cross-reader/comparator limit, not a normative
JavaScript violation. Preserve both ids and bytes; do not restrict ids to ASCII,
normalize strings, change the marker or silently make Python sorting normative.
The precise Unicode collation and its application to every textual report sort
remain a deferred 0.2.0 decision. This dossier does not adopt that decision.
The 0.1.1 lots may test preservation and record the known order disagreement;
they must not add an exact normative ordering oracle for this pair. The existing
ASCII-id comparison evidence does not establish agreement for arbitrary Unicode
ids or pointers. Comparator/provenance changes are outside this lot.
