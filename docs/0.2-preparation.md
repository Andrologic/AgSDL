# Preparing AgSDL 0.2

This guide explains the direction being explored for 0.2 and the steps before
adoption. It is informative and creates no specification rules.

The published version remains 0.1.1, with contract `agsdl-0.1.0`, as recorded in
[release status](../README.md#release-status-and-history). Candidate
`agsdl-exp-0016-c2` is an experiment implemented and compared by two readers.
Its scope has not been adopted as the scope of the future 0.2 release.

## The concept to evaluate

AgSDL describes an agentic system in a form that software can read and validate.
An editor can use this model to represent Agents, their instructions, tools and
relationships. Execution belongs to external software, within the boundaries
defined by the [project scope](scope.md).

The candidate tests a simple core with optional parts added when useful. The
table below explains its concepts; their exact rules remain in
[proposal 0016](../proposals/0016-kiss-experiment-0.2.md).

| Concept | What it describes in the candidate |
| --- | --- |
| Agent | Its ordered instructions, Interface and declared Tools. It can be described without selecting an engine. |
| Instructions and Interface | The content supplied to the Agent and its operations with typed inputs and outputs. Each value can be embedded in the Agent or referenced for sharing within the document. |
| Graph | Calls to Agents, data passed between them, success and failure paths, and declared human approvals. |
| Configuration | For a graph, the explicit engine choice for each Agent used, Tool implementations and adapters that apply its instructions. |
| Engine | The software intended to execute the Agent. Its identity and version are open; no default engine is imposed. |
| Tool and Implementation | A tool's contract and the concrete choice claimed to realize it. Declaring that choice does not prove its availability. |
| Execution | A concrete use of a graph and configuration by external software. Its live context, occurrences and state are not instances managed by these readers. |

For example, a writer Agent retains its instructions and Interface across two
configurations that select different engines. Each configuration declares its
adapters and Tool choices. Incompatibility remains visible; the reader neither
replaces a Tool nor translates options automatically. Selecting another engine
therefore does not guarantee identical behavior.

This modularity is local to one document. It does not yet provide module imports
or plugin loading. Required semantic extensions are reported as unsupported.
In the candidate, changing even just a configuration or formatting changes the
exact identity of the artifact and its named Definitions. A prospective execution
follows the rule: stop, modify, then start a new execution.

and grants no execution rights.

## What has been verified

The [assessment](../experimental/kiss-0.2/ASSESSMENT.md) records agreement between
two independent readers, Python and JavaScript, on 38 inputs and their expected
observations. These include invalid or incomplete inputs. Agreement is bounded
by that corpus; it proves neither engine support nor execution interoperability.

To try static reading, use the command in the
[Python guide](../experimental/kiss-0.2/readers/python/README.md) or the
[JavaScript guide](../experimental/kiss-0.2/readers/javascript/README.md).
The [corpus guide](../experimental/kiss-0.2/corpus/README.md) provides the
reproducible comparison command and explains its results. A reader's zero exit
code means it produced a report; each unit's results still need to be read to
determine what passed or failed.

## Recommendation to review

The recommendation is to retain the experimental core for a bounded first 0.2,
with reusable instructions, interfaces, sequences, explicit configurations and
declared human approvals. Imports, structured Skills and business conditions
would be deferred to later work. This recommendation still needs approval; it
removes no capability from the current specification.

Describing "write, then review" is covered by the experiment. Selecting another
Agent based on a business value returned by the reviewer would require an
additional condition. A call's success and failure paths do not replace that
business choice. The candidate's shareable instructions also do not replace the
structured Skill contract in 0.1.

The [assessment of tradeoffs](../experimental/kiss-0.2/ASSESSMENT.md#recommendations-and-remaining-decisions)
details the other choices: one Interface per Agent, optional actor for ungoverned
descriptions, textual action scopes, artifact-wide identity and repetition of
complete configurations. These consequences need to be accepted, or the
candidate revised, before adoption.

## Steps before the new release

The [roadmap](../ROADMAP.md#proposed-preparation-02) tracks the stages.
The proposed order is:

1. Approve the first 0.2 scope and document its differences from 0.1.
2. Record adoption of the chosen contract, then prepare the normative text,
   derived schemas, official examples and migration guide.
3. Align readers and corpus with that edition; obtain new evidence and an
   independent review. Retain experimental evidence under its original edition.
4. Verify the whole delivery, prepare release notes, then separately authorize
   publication of the corresponding revision and tag.

Capabilities outside the experiment, including parallelism and dynamic delegation,
remain future topics. This preparation provides no runtime, product integration
or automatic converter from 0.1.
