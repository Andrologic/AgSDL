# Candidate acceptance scenarios for 0.1.0 preparation

Status: non-normative research. These conceptual cases prepare future tests;
none has been executed. Proposals 0001 through 0011 considered in this research
remain proposed. User-plan
references for this preparation are **2, 7, 10, 35**; these numbers are not
requirement identifiers or a new acceptance commitment for the release.

Read the [implementation checklist](0.1.0-implementation-checklist.md) when
turning a case into evidence. [Decision 0001](../decisions/0001-specification-before-syntax.md)
puts the model before syntax. [Decision 0004](../decisions/0004-approved-design-directions.md)
accepts design directions, including bounded contract preparation, rather than
the detailed rules in [proposal 0011](../../proposals/0011-first-exchange-contract.md).
[Decision 0006](../decisions/0006-publish-version-0.0.2.md) does not adopt those
rules through publication.

The authorized lot A brief additionally records the user's directions: engines
are open, including custom engines, and there is no default engine. Their exact
contract remains undecided. This is the provenance of those directions here;
no existing decision is cited as having adopted an engine contract.

## Cases and candidate observations

Each row describes supplied conceptual facts, an operation, a candidate result,
and the decision still needed before executable acceptance criteria can exist.
REQ identifiers refer to the proposed [requirements baseline](../../proposals/0001-requirements-and-use-cases.md#mandatory-requirements).
The common blockers for every row are adoption of the relevant scope, input
representation, locations, and comparable report rules. Row-specific blockers
below are additional. Candidate observations are not current obligations.

## Preparing future fixtures

For each selected case, record the conceptual inputs and requested operation,
the adopted rule edition when one exists, the observed input boundary, and the
expected finding with its reason. Preserve the variants above as separate cases.
Mark unresolved decisions as blocked rather than assigning a pass/fail oracle.
Only after those decisions and representation are settled can fixtures and
executable assertions be authored. No serialization example or test result is
provided by this document.
