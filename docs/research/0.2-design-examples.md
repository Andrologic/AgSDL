# Candidate 0.2 design examples

**PROPOSED, not adopted, not implemented.** These sketches support
[proposal 0014](../../proposals/0014-minimal-core-0.2.md). They are JSON inside
Markdown, not official examples, schemas, reader fixtures or runtime evidence.
`PROPOSED-0014` is a discussion label, not an allocated contract marker. No
current AgSDL reader validates this candidate language. The proposed rules and
all module names below remain subject to maintainer arbitration.

## Reading the sketches

PROPOSED conventions: `definitions` is a map of unique local ids. Each value
has an explicit version and kind. `{"ref":"a"}` selects exactly that local
Definition; its scope is the document scope and its version is the selected
record's version. Each Definition belongs to the document boundary. Settings,
bindings and configuration ids occupy separately named local maps and are not
Definition identities. No lookup uses array order, latest version or defaults.
The root's id and version describe the document, not an execution occurrence.

The core minimum used here requires `contract`, `document`, `modules` and
`definitions`. An Agent requires `actsAs`, nonempty ordered `direction` and
nonempty `interfaces`. Instructions require format, target, application point
and body. Interfaces declare named operations with direction, mode and typed
ports. Principal's `description` is illustrative metadata; the explicit actor
reference and identity are not. Empty graphs, engine bindings and dependency
arrays are unnecessary for a core-only Agent description.

For the flow sketches, each call names its Agent, exposed Interface and operation.
Its bindings must match that operation's inputs; its output types come from the
operation. No coercion or omitted input is implied. `input` names a graph input;
`step`/`port` names a successful producer. Every path to a consumer must traverse
that producer's success edge. Edges determine ordering; all steps are reachable,
acyclic and end on success or failure. No failed call produces usable outputs.
These retain bounded G ideas, while deliberately omitting governed effects.

## Single Agent

This is a complete candidate core document. It describes an Agent without
promising a graph, engine selection or execution.

```json
{
  "contract": "PROPOSED-0014",
  "document": {"scope": "demo", "id": "solo", "version": "1"},
  "modules": [],
  "definitions": {
    "writer": {
      "kind": "Agent", "version": "1",
      "actsAs": {"ref": "operator"},
      "direction": [{"ref": "concise"}],
      "interfaces": [{"ref": "text"}]
    },
    "operator": {
      "kind": "Principal", "version": "1", "description": "Document operator"
    },
    "concise": {
      "kind": "Instructions", "version": "1",
      "target": "Agent", "at": "before-invoke",
      "format": {"identity": "example/plain-text", "version": "1"},
      "body": "Rewrite the supplied text concisely without adding facts."
    },
    "text": {
      "kind": "Interface", "version": "1",
      "operations": {
        "rewrite": {
          "direction": "inbound", "mode": "request-response",
          "inputs": {"text": "string"}, "outputs": {"text": "string"}
        }
      }
    }
  }
}
```

The prompt, names, descriptions and string ports illustrate the use case. The
separate accountable actor, direction and interface are proposed obligations.
Even with one Interface, a call must name it and its operation. The Principal
is not automatically the host user. No provider prompt role is inferred from
`before-invoke`; an engine Application would still be explicit.

## Two Agents in sequence

This second complete candidate document has its own boundary. The shared
Principal and Interface are intentional author choices. Different actors or
ports would need different Definitions. Writer output goes to reviewer input;
either failure terminates without using partial output.

```json
{
  "contract": "PROPOSED-0014",
  "document": {"scope": "demo", "id": "review-system", "version": "1"},
  "modules": [
    {"identity": "candidate/flow", "version": "1", "required": true}
  ],
  "definitions": {
    "writer": {
      "kind": "Agent", "version": "1", "actsAs": {"ref": "operator"},
      "direction": [{"ref": "draft"}], "interfaces": [{"ref": "text"}]
    },
    "reviewer": {
      "kind": "Agent", "version": "1", "actsAs": {"ref": "operator"},
      "direction": [{"ref": "review"}], "interfaces": [{"ref": "text"}]
    },
    "operator": {"kind": "Principal", "version": "1"},
    "draft": {
      "kind": "Instructions", "version": "1", "target": "Agent",
      "at": "before-invoke",
      "format": {"identity": "example/plain-text", "version": "1"},
      "body": "Rewrite the supplied text concisely without adding facts."
    },
    "review": {
      "kind": "Instructions", "version": "1", "target": "Agent",
      "at": "before-invoke",
      "format": {"identity": "example/plain-text", "version": "1"},
      "body": "Correct unsupported claims in the supplied draft."
    },
    "text": {
      "kind": "Interface", "version": "1",
      "operations": {
        "rewrite": {
          "direction": "inbound", "mode": "request-response",
          "inputs": {"text": "string"}, "outputs": {"text": "string"}
        }
      }
    },
    "pipeline": {
      "kind": "Flow", "version": "1", "entry": "draft-call",
      "inputs": {"text": "string"}, "outputs": {"text": "string"},
      "steps": [
        {
          "id": "draft-call", "kind": "invoke", "agent": {"ref": "writer"},
          "interface": {"ref": "text"}, "operation": "rewrite",
          "bindings": {"text": {"input": "text"}},
          "success": "review-call", "failure": "failed"
        },
        {
          "id": "review-call", "kind": "invoke", "agent": {"ref": "reviewer"},
          "interface": {"ref": "text"}, "operation": "rewrite",
          "bindings": {"text": {"step": "draft-call", "port": "text"}},
          "success": "done", "failure": "failed"
        },
        {
          "id": "done", "kind": "end", "outcome": "success",
          "bindings": {"text": {"step": "review-call", "port": "text"}}
        },
        {"id": "failed", "kind": "end", "outcome": "failure", "reason": "Call failed"}
      ]
    }
  }
}
```

This describes plain request/response text processing. It makes no assertion
about permission to perform external effects. It is not a lossless rewriting
of the official sequence's Action/Resource/context declarations. A governed
variant would explicitly require `effect-scope` and retain those facts.

## Same definitions and graph, two engine configurations

The following is an excerpt of additional top-level members for the sequence
above. Its `definitions` and `pipeline` stay byte-for-byte unchanged. The module
list for this combined candidate document explicitly contains both
`candidate/flow` version `1` and `candidate/bindings` version `1`, required true.
This presentation splits one document for readability; it is not an overlay
syntax, include directive or second authoring format.

```json
{
  "settings": {
    "plain": {
      "format": {"identity": "example/text-settings", "version": "1"},
      "value": {"output": "plain-text"}
    }
  },
  "bindings": {
    "writer-a": {
      "engine": {"identity": "example/engine-a", "version": "1"},
      "settings": "plain", "nativeOptions": {"trace": false},
      "applications": [
        {"content": {"ref": "draft"}, "adapter": {"identity": "example/content-a", "version": "1"}, "parameters": {}}
      ],
      "tools": []
    },
    "reviewer-b": {
      "engine": {"identity": "private/engine-b", "version": "7"},
      "settings": "plain", "nativeOptions": {"logging": "off"},
      "applications": [
        {"content": {"ref": "review"}, "adapter": {"identity": "private/content-b", "version": "2"}, "parameters": {}}
      ],
      "tools": []
    },
    "writer-b": {
      "engine": {"identity": "private/engine-b", "version": "7"},
      "settings": "plain", "nativeOptions": {"logging": "off"},
      "applications": [
        {"content": {"ref": "draft"}, "adapter": {"identity": "private/content-b", "version": "2"}, "parameters": {}}
      ],
      "tools": []
    },
    "reviewer-a": {
      "engine": {"identity": "example/engine-a", "version": "1"},
      "settings": "plain", "nativeOptions": {"trace": false},
      "applications": [
        {"content": {"ref": "review"}, "adapter": {"identity": "example/content-a", "version": "1"}, "parameters": {}}
      ],
      "tools": []
    }
  },
  "configurations": {
    "primary": {
      "graph": {"ref": "pipeline"},
      "agents": {"writer": "writer-a", "reviewer": "reviewer-b"}
    },
    "alternate": {
      "graph": {"ref": "pipeline"},
      "agents": {"writer": "writer-b", "reviewer": "reviewer-a"}
    }
  },
  "selected": "primary"
}
```

PROPOSED: each graph configuration maps every used Agent exactly once to a
complete binding and no unused Agent. A binding's Applications must match that
Agent's required direction and explicitly ordered prerequisites. Keys in
`agents` select Agent Definitions, values select binding records. `settings`
selects the whole settings record. Configuration selection is explicit; omission
selects nothing even if there is one configuration. An absent engine means not
provided and never picks a default. The engine field may be omitted only for an
explicitly incomplete binding; the four illustrated bindings all supply it.

These bindings have no capability claims, so settings, content format and adapter
support remain unknown, not proved portable. The illustrative settings contract
means output is requested as plain text; native logging values are opaque and
are not translations certified by AgSDL. An engine declaring support for the
same exact settings contract may share the record, subject to its other content
and Tool requirements. Different output semantics need a different contract.
Four Applications remain necessary because both the content and its engine
adapter matter. For these two configurations, binding indirection does not yet
save four binding declarations; it lets a third configuration reuse complete
choices without copying them. A complete shared value is the limit of reuse.

### Explicit incompatible Tool choice

This separate variant adds a Tool use to writer in the sequence. Both its
configurations still use the same modified Agent definitions and graph. This
excerpt shows the Tool Definition, the writer's additional `tools` references
and the complete Tool binding substituted for the empty tools array in
`writer-b`. The selected configuration is `alternate`. The other writer binding
would also need an explicit Tool binding before claiming completeness.

```json
{
  "toolDefinition": {
    "lookup": {
      "kind": "Tool", "version": "1",
      "inputs": {"query": "string"}, "outputs": {"text": "string"},
      "effects": "none", "failures": ["unavailable"],
      "requires": [{"identity": "example/local-lookup", "version": "1"}]
    }
  },
  "agentTools": [{"ref": "lookup"}],
  "bindingTools": [
    {
      "tool": {"ref": "lookup"},
      "implementation": {"identity": "private/lookup-b", "version": "1"},
      "parameters": {},
      "claims": [
        {
          "capability": {"identity": "example/local-lookup", "version": "1"},
          "status": "unsupported", "evidence": null
        }
      ]
    }
  ]
}
```

The three wrapper names label excerpts, not candidate document fields or a
transformation language. Lookup here is an illustrative pure local lookup;
external or unknown effects would require explicit effect-scope declarations.
The chosen implementation explicitly declares a required capability unsupported.
Keep the Tool, selection, requirement and claim intact. Report declared
incompatibility for that choice alongside any other unknown support; do not
substitute another implementation, erase the Tool, or conclude that the document
structure is invalid. An actual supported claim would still require separate
evidence assessment before any readiness claim.

### Reusable Skill without an executable subgraph

A Skill variant would explicitly add `candidate/skills` version `1` to the
required modules and use the following Definition. It would put the references
`draft`, then `checked-draft` in writer's direction and in each selected writer
binding's Applications, with explicit engine-specific adapters. The `lookup`
Tool above must be declared and bound too. These are authored additions, not
implicit expansion of a Skill or instructions to a runtime.

```json
{
  "checked-draft": {
    "kind": "Skill", "version": "1",
    "inputs": {"text": "string"}, "outputs": {"text": "string"},
    "preconditions": "A source text is supplied.",
    "completion": "Claims in the draft have been checked against local lookup.",
    "dependencies": [{"ref": "draft"}], "tools": [{"ref": "lookup"}]
  }
}
```

The prerequisite graph must be acyclic. Missing earlier Applications are errors,
not a request to insert them. This reuses content and Tool contracts, without
turning Skill ports or completion prose into flow scheduling or verified results.

## Comparison with the official examples

Observed counts below describe the files, not a minimum imposed on every system.
The candidate trades some old declaration coverage for a smaller basic flow;
that tradeoff must not be represented as compression alone.

| Use | Observed 0.1.0 file | Obligations versus illustration | Candidate effect |
| --- | --- | --- | --- |
| Empty boundary | [minimal-document.json](../../examples/0.1.0/minimal-document.json): zero Definitions and six required collection fields. | Definitions, relations, exports, dependencies, unresolved and extensions are present even empty; no Agent is required. | Four envelope members in the candidate convention, with no unrelated empty collections. An empty boundary is not an Agent use case. |
| One Agent | [single-agent.json](../../examples/0.1.0/single-agent.json): four Definitions and three relations. | Agent, Principal, Interface and Role are illustrated. One actsAs, direction and exposes link are required; Role is replaceable by another allowed direction kind. Interface operations are not D-minimum payload obligations. | Still four Definitions and three explicit Agent links. Repeated key triples, owners and expectedKind disappear through typed fields and local references. The candidate adds a concrete prompt and operation contract, so it is more informative, not just shorter. |
| Two calls | [two-agent-sequence.json](../../examples/0.1.0/two-agent-sequence.json): ten Definitions, six relations, two invokes and two terminals. | Two Principals, two Actions and two operations are illustrative choices. G requires a Principal, Action, nonempty Resource refs, context, input/output maps and explicit operation at each invoke. The selected operation repeats Action and ports. | Seven Definitions, six Agent links, two invokes and two terminals. Sharing a Principal is an author choice already possible in 0.1.0, not a language saving. Dropping Action/Resource/context changes scope. Removing repeated ports and Principal is the actual duplication saving. |
| Engine switch | [general-purpose-system.json](../../examples/0.1.0/general-purpose-system.json): fourteen Definitions, eight relations and two configurations with four AgentBindings total. | R requires per-Agent assignments, parameters, requirements, claims, tools and applications arrays; content/Tool use determines nonempty entries. Temperature, logging, fake evidence hashes and the chosen engine names are illustrative. | Settings value defined once; graph and Agent definitions stay fixed. Four complete bindings remain in this example. Extra named records and lookups are a cost; sharing helps when complete choices recur, not automatically for two distinct choices. |

The general-purpose example also includes reusable content and Tools, plus an
unused ApprovalRequirement Definition. Its graph has two invokes and two end
steps; it exercises neither conditions nor approval gates. The candidate
sequence does not replace its content and Tool coverage or prove equivalent
behavior. Both designs require explicit content application
and implementation choice when those features are used. No line-count reduction
establishes better semantics or interoperability.

## Assembly experiment

**PROPOSED experiment only, outside the recommended 0.2 minimum.** In a separate
variant of the two-Agent document, keep writer, reviewer, their directions,
Principal and text Interface. Rename its `pipeline` Definition to `polish`,
change its kind from Flow to Assembly, and give it
`interface: {"ref":"text"}` and `operation: "rewrite"`. Its existing inputs,
outputs and two-call body remain explicit and must exactly match that operation.
This describes one static candidate document, not an authoring rewrite facility.
Declare both `candidate/flow` and `candidate/assembly-experiment` version `1` as
required modules. The following new Flow is the outer graph, using the assembly
twice on independent inputs, sequentially.

```json
{
  "batch": {
    "kind": "Flow", "version": "1", "entry": "first",
    "inputs": {"left": "string", "right": "string"},
    "outputs": {"left": "string", "right": "string"},
    "steps": [
      {
        "id": "first", "kind": "call-assembly", "assembly": {"ref": "polish"},
        "interface": {"ref": "text"}, "operation": "rewrite",
        "bindings": {"text": {"input": "left"}},
        "success": "second", "failure": "failed"
      },
      {
        "id": "second", "kind": "call-assembly", "assembly": {"ref": "polish"},
        "interface": {"ref": "text"}, "operation": "rewrite",
        "bindings": {"text": {"input": "right"}},
        "success": "done", "failure": "failed"
      },
      {
        "id": "done", "kind": "end", "outcome": "success",
        "bindings": {
          "left": {"step": "first", "port": "text"},
          "right": {"step": "second", "port": "text"}
        }
      },
      {"id": "failed", "kind": "end", "outcome": "failure", "reason": "Assembly failed"}
    ]
  }
}
```

PROPOSED experiment rules: the assembly contains only ordinary invokes and end
steps; it calls no assembly and cannot name itself. Targets are fixed references,
with no recursion or dynamic delegation. Internal inputs come only from the
assembly's declared input ports, never implicit outer context. Internal success
binds exactly the declared outputs; internal failure follows the outer call's
failure edge and exposes no outputs. Outer consumers can name only the assembly
call's public output ports, not its internal steps. A call site is identified by
an explicit path such as `first/draft-call` or `second/draft-call`; these static
paths are not execution occurrence ids. The two sites share Agent Definitions
and thus share their per-Agent binding in a selected configuration of `batch`.
Different per-site engines require distinct Agent Definitions, not hidden overrides.
A bindings-aware experiment must enumerate both statically referenced bodies
when checking configuration completeness. The core flow module alone cannot
claim to understand `call-assembly`.

Without an assembly, the flattened outer flow needs four invoke records and
wiring for both copies. With it, there are still four call-like records, two
internal invokes and two outer calls, plus an extra boundary and two extra end
records across the two bodies. Only the internal wiring and its maintenance are
shared. At two uses, this does not clearly simplify the whole document. Larger
repeated units might benefit, but require additional evidence before adoption.
The experiment adds interface agreement, path scoping, failure propagation and
binding enumeration obligations. It adds no runtime support, implementation
commitment or promise of assembly delivery in 0.2.
