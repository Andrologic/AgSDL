# Implementation evidence prerequisites for 0.1.0 preparation

Status: non-normative preparation checklist. This records questions and evidence
to prepare, not adopted requirements or a claim of implementation readiness.
It accompanies the [candidate scenarios](0.1.0-acceptance-scenarios.md), which
record acquired directions and case-specific blockers. Proposals 0001 through
0011 considered in this preparation remain proposed; [Decision 0006](../decisions/0006-publish-version-0.0.2.md)
does not adopt them.

User-plan references are **2, 7, 10, 35**. Prerequisite references are
**3, 4, 5, 14, 16, 19, 22–28, 33**. They retain the user's numbering as
cross-references only. They are not REQ identifiers, new obligations, or a
restatement of the whole plan.

## Before implementing acceptance tests

- [ ] Identify the maintainer-adopted scope and rules for each selected case.
  Track unresolved choices in [proposal 0011](../../proposals/0011-first-exchange-contract.md#choices-required-before-adoption)
  explicitly, especially Identity meaning, scope/equality, deferrals, unknown
  information, preservation, and verdicts. Candidate text is not an oracle.
- [ ] After model review, settle the representation, payload boundaries and
  locations needed by the selected operation, following
  [Decision 0001](../decisions/0001-specification-before-syntax.md). This checklist
  supplies no grammar, schema, feature identity, or graph behavior.
- [ ] Prepare positive, negative, and unavailable-evidence variants only for
  adopted checks. Record exact input revisions, operation, rule edition,
  coverage, expected findings and exclusions before collecting actual results.
  Keep evidence unavailable until a test or inspection has really occurred.

These items are pending preparation, not a claim that their decisions have
already been made. Proposed REQ-006–009 and REQ-030 in the
[requirements baseline](../../proposals/0001-requirements-and-use-cases.md#mandatory-requirements)
provide traceability; [Decision 0004](../decisions/0004-approved-design-directions.md)
provides the accepted direction to use bounded features/profiles and phases.

## Independent evidence and completion boundaries

- [ ] For a future two-reader comparison, identify independently implemented
  readers and the code paths behind each result. Two applications using the
  same SDK reader provide evidence about one shared reader, not two independent
  readers. Two application names, wrappers, or runs do not establish reader
  independence. This is evidence planning, not a request to modify either app.
- [ ] Once common fixtures and adopted rules exist, compare portable meaning,
  covered structural failures and extension identification, as targeted by the
  [scope success condition](../scope.md#success-condition). Record disagreements
  and uncovered checks. No such comparison has been run by this preparation.
- [ ] Keep repository verification separate from language evidence.
  [scripts/check.sh](../../scripts/check.sh), described in
  [CONTRIBUTING.md](../../CONTRIBUTING.md#verification), is a repository check.
  Its success is not parser support, conformance, interoperability, or execution
  evidence. [Proposal 0003](../../proposals/0003-conformance-and-versioning.md#evidence-boundaries)
  explains the proposed limits of structural and execution evidence.

Preparation is reviewable when every selected scenario has sources, a stated
operation and visible decision blockers. Implementation acceptance remains
pending adopted contracts, executable fixtures and independently collected
results; completing these documents does not close those prerequisites.
