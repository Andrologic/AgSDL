# MCP 2026-07-28 binding research

Status: research note, non-normative
Last reviewed: 2026-09-02

## Purpose and source boundary

This note examines the current stable Model Context Protocol revision as input
to an AgSDL binding proposal. It does not define AgSDL syntax, make an MCP
implementation conformant, or change the AgSDL specification.

The reviewed revision is `2026-07-28`. The MCP project identifies its
[2026-07-28 release](https://github.com/modelcontextprotocol/modelcontextprotocol/releases/tag/2026-07-28)
as stable. The release points to the dated
[specification](https://modelcontextprotocol.io/specification/2026-07-28/),
whose TypeScript schema is the authoritative message definition. The
[release schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/2026-07-28/schema/2026-07-28/schema.ts)
is therefore the primary machine-readable reference used here. All sources in
this note were accessed on 2026-09-02.

Source facts below summarize MCP. AgSDL assessments are conclusions for this
project. They do not add requirements to MCP.

## Protocol and capability model

### Source facts

The [MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture)
separates hosts, clients, and servers. A host manages security, consent,
authorization, context, and client lifecycles. Each client maintains a
one-to-one relationship with one server.

MCP uses JSON-RPC 2.0. In revision `2026-07-28`, the core is stateless and has
no initialization handshake. Every client request carries the protocol version
and relevant client capabilities in `_meta`. A server cannot infer protocol
version, client identity, capabilities, conversation, or task state from a
connection or an earlier request. Cross-request state uses an explicit handle.

Servers must implement `server/discover`. A client may call it to obtain
supported protocol versions, server capabilities, and self-reported server
identity. A client may instead send another request directly and handle
`UnsupportedProtocolVersionError`. Server identity is informational and must
not drive security decisions. Discovery results may be cached according to the
returned cache scope and lifetime.

The [versioning and compatibility
rules](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)
distinguish modern revisions, `2026-07-28` and later, from handshake-based
legacy revisions, `2025-11-25` and earlier. A dual-era client or server follows
transport-specific probing and fallback rules. A recognized modern error is a
version-negotiation response, not a signal to fall back to legacy behavior.

Client capabilities are supplied on each request. Server capabilities are
returned by discovery. Core capabilities and settings are directional. For
example, a server advertises tools, resources, and prompts, while a client
advertises elicitation or sampling. A server must not require a client
capability omitted from that request. It reports the missing capability with
`MissingRequiredClientCapabilityError`.

### AgSDL assessment

An AgSDL MCP binding needs an exact MCP revision, protocol era, transport, and
directional capability requirements. A discovered capability is runtime
evidence about one server response. It is not an AgSDL definition, authority
grant, security capability claim, or proof of correct implementation.

The binding cannot treat connection establishment as capability negotiation
for revision `2026-07-28`. It must account for per-request client capabilities
and for server discovery or explicit version-error recovery. Supporting a
legacy revision is a separate binding variant because initialization, sessions,
subscriptions, and server-to-client interaction differ materially.

## Server features

### Tools

MCP servers advertise the `tools` capability, list tool contracts with
`tools/list`, and accept invocations through `tools/call`. An MCP tool has a
name, input schema, optional output schema, descriptive metadata, and optional
behavior annotations. Results may contain structured content and typed content
blocks. Tool errors reported in a successful JSON-RPC result are distinct from
protocol errors.

The [tool specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
states that tools are model-controlled as an interaction convention. It does
not require a particular host user interface. It also warns that tool
descriptions and annotations are untrusted unless the server is trusted.

An MCP tool contract can identify how an AgSDL Tool is reached. It does not
replace the AgSDL Action, Effect, Resource, Policy, or Authorization requirement
associated with using that tool. MCP annotations are hints, not verified effect
or safety declarations.

### Resources

MCP servers advertise the `resources` capability. They can list URI-identified
resources and URI templates and return text or binary content through
`resources/read`. The visible catalog may depend on per-request authorization.
Catalogs can change. Resource links returned by tools need not appear in
`resources/list`.

The [resource specification](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
defines protocol resources as application-controlled context. An MCP resource
URI is therefore an external identifier, not proof of ownership, provenance,
truth, freshness, or access authority. An AgSDL Resource or Knowledge mapping
must add those AgSDL facts where they matter.

### Prompts

MCP servers advertise the `prompts` capability, expose prompt metadata through
`prompts/list`, and resolve a named prompt with arguments through `prompts/get`.
The [prompt specification](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)
describes prompts as user-controlled because the user normally chooses when to
use them. The server authors the returned content, and MCP does not mandate the
host interaction design.

An author may incorporate pinned MCP prompt content into an Instructions
definition before resolution. Content returned by `prompts/get` during an
execution remains message content and cannot alter that definition. Discovery
or user selection does not make prompt content trusted, give it AgSDL
instruction precedence, or authorize actions suggested by the content.

### Catalog changes and subscriptions

Tools, resources, and prompts may advertise `listChanged`. Revision
`2026-07-28` uses `subscriptions/listen` for list changes and resource updates.
The client selects notification filters and the server acknowledges the
subscription with an identifier. The subscription is a long-lived request
whose state belongs to that request, not to the transport connection. Losing
the stream requires a new request.

An AgSDL binding that depends on timely catalog changes needs a freshness and
recovery policy. `listChanged` support alone does not state how stale data is
handled after a stream failure.

## Multi round-trip requests

The [Multi Round-Trip Requests
pattern](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)
replaces server-initiated JSON-RPC requests. Only `tools/call`, `resources/read`,
and `prompts/get` may return `InputRequiredResult`. The result carries keyed
input requests for roots, sampling, or elicitation. The client processes those
requests and retries the original method with keyed responses and any opaque
`requestState`. The retry has a new JSON-RPC request identifier.

`requestState` is server-created continuation data. It is not an MCP session or
an AgSDL State definition. A binding must preserve it opaquely and must not use
it as proof that authorization, approval, or an action occurrence remains valid
across retries.

### Elicitation

The [elicitation feature](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)
allows a server to request user input through form or URL modes. Clients declare
the modes they support on each request. Responses can accept, decline, or
cancel. Elicitation is an information exchange. It is not, by itself, an AgSDL
Approval decision, Consent record, authentication event, or Authority grant.

### Sampling and roots

The [sampling feature](https://modelcontextprotocol.io/specification/2026-07-28/client/sampling)
allows a server to request model generation through the client. Sampling can
include a multi-turn tool loop. The feature and its context-inclusion option are
deprecated in `2026-07-28`; new implementations should use model-provider APIs
instead.

The [roots feature](https://modelcontextprotocol.io/specification/2026-07-28/client/roots)
is also deprecated in `2026-07-28`. Roots are informational filesystem hints,
not an access-control boundary. New implementations should pass directories or
files through tool parameters, resource URIs, or server configuration.

AgSDL should represent sampling and roots only for compatibility with an
identified binding that needs them. A sampling loop needs an AgSDL termination
and failure policy when its iteration affects portable behavior. A root never
satisfies an AgSDL sandbox, Resource, Policy, or Authority declaration.

## Extensions and tasks

The [MCP extension framework](https://modelcontextprotocol.io/extensions/overview)
uses owner-qualified identifiers in the `extensions` capability map. Both
parties opt in. Each extension owns the schema of its settings object and its
fallback behavior. Extensions evolve independently from the core protocol.
Official extensions live in MCP organization repositories. Experimental
extensions use a separate incubation path and status.

The `2026-07-28` client and server capability objects retain an `experimental`
map for non-standard capabilities. This map is not the formal extension
registry. An AgSDL binding should preserve such entries as
implementation-specific information unless an identified external contract
defines them. It should not promote them to stable core capabilities.

Revision `2026-07-28` moved Tasks out of the core into the official
`io.modelcontextprotocol/tasks` extension. The [Tasks
extension](https://modelcontextprotocol.io/extensions/tasks/overview) provides
durable handles, polling, cooperative cancellation, terminal states, and
mid-flight input. It requires explicit client and server support.
The published `2026-07-28` extension applies task-augmented results to
`tools/call`; support for Tasks does not make every MCP operation task-capable.

An MCP capability entry does not supply the independent extension contract
version required by AgSDL proposal 0003. An AgSDL binding must reference the
extension specification edition or immutable content identity separately.
Experimental status must remain visible. An MCP Task handle is execution data
and must not be mistaken for an AgSDL Work item, Control flow, or State
definition.

## Transport and authorization

MCP `2026-07-28` standardizes stdio and Streamable HTTP transports. The
[transport overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)
states that a transport frames and delivers messages but does not change their
meaning. Streamable HTTP mirrors body metadata into HTTP headers, while the
message body remains authoritative. The HTTP binding rejects a mismatch between
the `MCP-Protocol-Version` header and body metadata with `HeaderMismatchError`.

The [authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
is optional and applies to HTTP-based transports. It uses OAuth 2.1 and related
standards for protected-resource and authorization-server discovery, client
registration, resource indicators, bearer tokens, scope challenges, and issuer
and audience checks. Dynamic client registration remains only for backward
compatibility. Stdio should obtain credentials from the environment rather than
apply the HTTP authorization flow.

Every protected HTTP request carries authorization. The server validates that
the token is intended for that MCP server and must not accept or transit a token
for another resource. A `401` denotes missing or invalid authorization. A `403`
can carry an insufficient-scope challenge for step-up authorization.

OAuth credentials and scopes are transport authorization inputs. They neither
define nor replace AgSDL Principal, Identity, Authentication evidence,
Authority grant, Policy, Approval, or Authorization decision. The binding must
refer to credentials without embedding secrets and must say how MCP
authorization evidence contributes to an AgSDL decision. It must not interpret
scope discovery or a successful tool call as proof that the action complied
with all AgSDL policy.

## Resulting design constraints

The research supports these constraints for an AgSDL MCP proposal:

- pin the MCP core revision and every extension contract independently;
- identify the protocol era and transport rather than inferring them from an
  endpoint;
- separate required server capabilities from client capabilities and evaluate
  the latter on every request;
- map named tools, resource URIs or templates, and prompts explicitly when
  portable behavior depends on them;
- keep MCP contracts external and keep AgSDL action, effect, trust, policy, and
  authority semantics in AgSDL;
- declare failure or degradation before execution for missing versions,
  capabilities, extension support, catalog entries, subscriptions, or
  authorization;
- model MRTR as a bounded external protocol sequence when it changes portable
  behavior;
- treat elicitation, sampling, roots, tasks, discovery, and annotations according
  to their narrow MCP meanings; and
- require execution evidence before claiming that an adapter or runtime
  interoperates with an MCP implementation.
