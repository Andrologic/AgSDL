# A2A 1.0.1 integration research

Status: research note, non-normative
Last reviewed: 2026-09-02

## Question

This note examines what AgSDL can safely say about an Agent2Agent Protocol
integration. It reviews the stable A2A `v1.0.1` release and separates A2A's
external server contract from AgSDL's proposed complete system model.

## Reviewed sources

The A2A Project published `v1.0.1` from commit
`3303592588e388e62e0f69f701af531d2f4e3991`. The release identifies three
specification fixes over `v1.0.0`: the preferred HTTP media type, transcoding
errors, and TaskStatus values.

Primary sources:

- [A2A v1.0.1 release](https://github.com/a2aproject/A2A/releases/tag/v1.0.1)
- [A2A v1.0.1 specification](https://github.com/a2aproject/A2A/blob/v1.0.1/docs/specification.md)
- [normative v1.0.1 Protocol Buffer definition](https://github.com/a2aproject/A2A/blob/v1.0.1/specification/a2a.proto)
- [A2A v1.0 migration note](https://github.com/a2aproject/A2A/blob/v1.0.1/docs/whats-new-v1.md)
- [official A2A TCK](https://github.com/a2aproject/a2a-tck)

The tagged repository's `specification/a2a.proto` file is the authoritative
data model. Generated JSON artifacts and SDK types are derived, non-normative
forms. The source hashes recorded in `a2a-v1.0.1.sha256` let a reviewer confirm
that a local upstream checkout is the edition reviewed here.

The official TCK was also inspected. On 2026-09-02, its `main` branch was at
commit `263b9cfaf16a554bdfb166a7ba5b67716e946349`, while the available 1.0 tags
were `1.0.0.alpha1` and `1.0.0.alpha2`. A report from that moving branch or an
alpha tag can supply bounded implementation evidence. It is not, by itself,
stable proof of complete A2A 1.0.1 conformance.

## Findings in the tagged sources

The reviewed tag contains several conflicts that affect mechanical consumers:

- the HTTP annotation on `SubscribeToTask` in `a2a.proto` uses
  `GET /tasks/{id}:subscribe`, while the HTTP mapping table and HTTP+JSON section
  use `POST /tasks/{id}:subscribe`; and
- the AgentCard proto field is `security_requirements`, which serializes as
  `securityRequirements` under the stated ProtoJSON naming rule, while the
  sample Agent Card uses `security`; and
- the general SendStreamingMessage rule closes a task lifecycle stream only at
  a terminal state, while the HTTP+JSON streaming section closes it at a
  terminal or interrupted state; and
- the TaskState proto comment describes `TASK_STATE_AUTH_REQUIRED` as requiring
  authentication, while the in-task authorization section uses the same state
  to delegate fulfillment of an authorization request.

These are source findings, not AgSDL corrections to A2A. The proto remains the
authority for data-object shape. The method and closure conflicts cross general
operation rules and binding-specific text. The authentication-versus-
authorization conflict crosses the state description and its procedural use.
An AgSDL processor must report the affected behavior as indeterminate unless a
pinned upstream erratum, binding edition, explicit external procedure, or
targeted runtime test establishes the interpretation it used. It must not
normalize any conflict silently.

## Version identity

A2A uses two related version identities:

- `1.0.1` identifies the published specification edition.
- `1.0` is the protocol version exchanged by clients and servers and declared
  by an AgentInterface.

AgentCard `version` is a third identity: the remote server's own software or
service version. It does not select an A2A protocol edition.

Patch numbers do not affect protocol compatibility and should not appear in
requests, responses, or Agent Cards. An AgSDL binding therefore needs both
identities. Recording only `1.0` cannot identify which corrected specification
text or proto a validator applied.

Clients send protocol version `1.0` through the binding's A2A-Version service
parameter. An absent value makes a server assume protocol version `0.3`. A
resolved 1.0 binding must therefore record and test explicit version
transmission rather than rely on omission.

## External description boundary

An Agent Card describes one remotely reachable A2A server. It gives a human
name and description, server version, supported interfaces, optional provider,
capabilities, security schemes and requirements, media types, advertised
skills, optional signatures, and optional documentation or icon links.

The card does not disclose the server's internal agents, models, prompts,
tools, memory, control flow, topology, policies, deployments, or evaluation
definitions. A card may describe a boundary implemented by one agent, a
composite agent, or an entire system. Its use of the word `agent` does not
resolve that choice.

AgSDL must consequently treat an Agent Card as an external boundary
description. A processor cannot synthesize a complete AgSDL System or Agent
definition from it. An AgSDL author may separately assert that a known System
or Agent exposes the card, but that assertion needs its own identity and
evidence.

## Agent Card and interfaces

An A2A server must publish an Agent Card. A public card can be discovered at the
well-known URI, in a registry, or through direct configuration. If the public
card declares `capabilities.extendedAgentCard`, an authenticated client can
request a more detailed card. The public and extended cards are distinct
observations. A processor must not silently merge fields obtained under
different authentication or freshness conditions.

Each AgentInterface combines four concerns:

- an endpoint URL;
- a protocol binding identifier;
- an optional opaque tenant routing value; and
- the A2A protocol version.

The standard binding identifiers are `JSONRPC`, `GRPC`, and `HTTP+JSON`.
Custom bindings should use versioned URIs. When one card lists several
interfaces, A2A requires equivalent functionality, behavior, error mapping,
and authentication across them. This is a runtime requirement, not a fact that
the card proves.

An AgSDL Interface is transport-neutral. An A2A AgentInterface therefore fits
a resolved transport or deployment binding for an external interface. It does
not replace the portable Interface definition or prove that all advertised
bindings behave equivalently.

The A2A application protocol defines this operation set independently of the
selected binding:

| Concern | A2A operations |
| --- | --- |
| Start or continue work | SendMessage, SendStreamingMessage |
| Observe work | GetTask, ListTasks, SubscribeToTask |
| Request cancellation | CancelTask |
| Manage webhooks | Create, Get, List, and Delete TaskPushNotificationConfig |
| Authenticated discovery | GetExtendedAgentCard |

Streaming, push notification, and extended-card operations depend on the
corresponding advertised capabilities. Standard bindings map the same
application operations to JSON-RPC methods, gRPC methods, or HTTP resources.
An AgSDL external binding specification should reference this operation contract
instead of copying each request and response shape.

JSON-RPC uses `application/json`. The v1.0.1 correction makes
`application/a2a+json` the preferred HTTP+JSON media type. HTTP streaming uses
`text/event-stream`. Canonical v1 HTTP+JSON paths omit the former `/v1` prefix.
These binding facts belong to the selected AgentInterface, not to the portable
AgSDL Interface contract.

## Advertised skills

AgentSkill is descriptive service metadata. It has an identifier, name,
description, tags, examples, optional input and output media-type overrides,
and optional security requirements. A2A has no operation that invokes an
AgentSkill by its identifier. A client sends a Message and the server chooses
how to handle it.

The following concepts remain separate:

- an A2A AgentSkill advertised at an external boundary;
- an AgSDL Skill that composes reusable behavior;
- an AgSDL Interface operation;
- a Tool operation;
- an Authority grant; and
- a runtime implementation feature.

An author may declare a checked correspondence between an AgentSkill and an
AgSDL definition. A processor must not infer one from equal names, tags, media
types, or examples.

## Tasks, messages, and artifacts

An A2A Task is a server-generated runtime record for work. It contains a task
identifier, optional context identifier, current status, outputs, optional
message history, and metadata. It is not an AgSDL Control flow or a reusable
definition.

A2A Message is one client-to-server or server-to-client communication turn. Its
`ROLE_USER` and `ROLE_AGENT` values identify protocol sides. They do not name an
AgSDL Principal or prove an authenticated identity. Message identifiers,
context identifiers, task identifiers, and referenced task identifiers support
correlation, but A2A permits the server to omit some messages from task history.
Critical delivery evidence cannot rely on Message history alone.

A2A recommends Artifacts for task outputs and Messages for communication.
Artifacts can arrive through several update events with append and last-chunk
markers. An A2A Artifact is therefore mutable while it is assembled. It can map
to an AgSDL immutable artifact only after assembly is complete and the AgSDL
record supplies content identity or an integrity reference. Before then, it is
execution data.

## Long-running work and update delivery

SendMessage can return a direct Message or a Task. For a Task, processing may
continue after the response. Clients can observe it by polling GetTask, using a
stream, or registering push notifications.

Streaming is a delivery mechanism. A task lifecycle stream begins with a Task,
then carries status or artifact updates. The general operation rule closes it
on a terminal state, while the HTTP+JSON section also closes it on an
interrupted state. A 1.0.1 HTTP+JSON binding must record this behavior as an
upstream conflict until an erratum or targeted runtime evidence selects the
observed behavior. SubscribeToTask starts with the current Task to close the
observation gap between polling and subscription. The specification permits
several concurrent streams and requires them to receive the same events in the
same order. The task lifecycle remains independent of any stream.

Each StreamResponse contains exactly one Task, Message, status update, or
artifact update. A2A 1.0 removed the earlier `kind` discriminator and the
TaskStatusUpdateEvent `final` flag. Stream closure after a terminal state now
signals completion.

Push notifications deliver the same StreamResponse variants to a registered
HTTPS webhook. The registration contains a callback URL, token, and optional
authentication material. Those runtime values are sensitive occurrences. An
AgSDL definition may declare their binding and secret requirements but must not
embed live credentials.

The server attempts each configured webhook at least once, so duplicates may
occur. The receiver acknowledges success with HTTP 2xx, verifies the Task ID and
sender, and processes deliveries idempotently. The server validates webhook
URLs against SSRF. A2A permits retries and eventual abandonment, so the
protocol does not promise exactly-once or guaranteed eventual delivery.

Neither streaming nor push notification support defines an AgSDL Protocol by
itself. An AgSDL Protocol is needed only when portable system meaning depends on
a multi-message sequence and its participant roles or states.

## Task states

The authoritative proto defines these states:

| A2A state | Classification in A2A 1.0.1 | AgSDL consequence |
| --- | --- | --- |
| `TASK_STATE_UNSPECIFIED` | unknown or indeterminate | Never infer a terminal outcome. |
| `TASK_STATE_SUBMITTED` | active | The work was acknowledged, not completed. |
| `TASK_STATE_WORKING` | active | Processing is in progress. |
| `TASK_STATE_INPUT_REQUIRED` | interrupted | The client may supply more input. |
| `TASK_STATE_AUTH_REQUIRED` | interrupted | Authentication or in-task authorization remains unresolved; the binding must record which source semantics and external procedure apply. |
| `TASK_STATE_COMPLETED` | terminal success | May support an AgSDL success observation when an explicit mapping exists. |
| `TASK_STATE_FAILED` | terminal error | May support an AgSDL failure observation when an explicit mapping exists. |
| `TASK_STATE_CANCELED` | terminal cancellation | Does not prove rollback or absence of external effects. |
| `TASK_STATE_REJECTED` | terminal refusal | Does not imply authentication or authorization denial. |

Blocking SendMessage returns on either a terminal or interrupted state.
Interrupted does not mean terminal. Terminal task status also does not establish
that an AgSDL System outcome or internal control flow reached a corresponding
terminal step unless the binding declares and tests that mapping.

## Extensions

AgentExtension uses a URI identity, description, required flag, and optional
parameters. Clients opt in through binding-specific service parameters.
Messages and Artifacts can identify the extension URIs that contributed their
metadata.

A breaking extension change requires a new URI. Unsupported optional versions
may be ignored for an interaction, but there is no automatic fallback to an
older version. A required extension that the client did not declare must fail
with ExtensionSupportRequiredError.

This is close to AgSDL's proposed required-versus-optional extension handling,
but the scopes differ. A2A extension support applies to a protocol interaction.
AgSDL extension support applies to an operation performed on a system
description. A binding must record both scopes rather than collapse them.

## Security

Production A2A deployments must use encrypted transport. Agent Cards declare
API key, HTTP authentication, OAuth 2.0, OpenID Connect, or mutual TLS schemes
and the requirements that combine them. Extended Agent Card retrieval requires
authentication described by the public card. Agent Cards may carry JWS
signatures over a prescribed canonical form.

These declarations describe authentication requirements. They do not grant
authority. A2A leaves request authorization to server policy and permits it to
consider skills, task actions, data policy, and OAuth scopes.

The server applies authorization to every A2A operation. Task listing, lookup,
cancellation, subscription, and push configuration are scoped to the
authenticated caller. Authorization checks occur before a query or response
can reveal that an inaccessible resource exists.

For authorization needed during a task, the server uses
`TASK_STATE_AUTH_REQUIRED` and normally receives credentials out of band. An
in-band credential exchange needs prior negotiation or an extension. Passing a
credential through several A2A agents exposes it to each intermediary unless
the credential is bound and protected for the originating server.

An AgSDL binding must keep these items distinct:

- advertised authentication scheme;
- observed authentication evidence;
- Authority grant;
- Authorization requirement and decision;
- credential or secret reference; and
- transport protection evidence.

Agent Card signatures can support provenance and integrity checks. A valid
signature does not establish trust in the signer, freshness, authorization, or
runtime conformance.

## Verification boundary

Three checks have different subjects:

1. Source verification confirms the exact A2A specification and proto reviewed.
2. Binding validation checks AgSDL references, version identities, explicit
   mappings, and required evidence once AgSDL has a serialization and accepted
   external binding specification.
3. Runtime tests exercise an A2A server through every claimed interface and
   optional capability.

The script `scripts/verify-a2a-1.0.1-sources.sh` implements the first check. It
does not validate an Agent Card or server. The official TCK can contribute to
the third check, but its suite version, commit, selected transports, skipped
tests, system under test, and report must be recorded. AgSDL-specific mapping
tests remain necessary because the A2A TCK cannot see an internal AgSDL graph.

No executable AgSDL binding validator is possible until AgSDL selects a
serialization and accepts normative binding rules. Proposal 0005 defines the
candidate semantics and the evidence needed before any future implementation
can make a bounded claim.
