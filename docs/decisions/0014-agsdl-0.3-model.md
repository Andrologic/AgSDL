# 0014. The AgSDL 0.3 model

Status: accepted for the 0.3.0 draft.

AgSDL 0.1 and 0.2 were written quickly. In 0.2, agents were configured
through abstract bindings and opaque settings, routing could read any field of
any result, and joins, steering and compositions carried heavy bookkeeping.
AgSDL is not yet used by third parties, so 0.3 breaks compatibility to fix the
model.

## 1. The graph links missions; the agent conducts its mission

A step gives a mission to an agent. Planning, executing and checking that
mission happen inside the agent, in its own conversation: no harness studied
models phases as a graph, and splitting one mission into steps forces either
lost context or a graph inside the graph. Different missions are different
agents; they exchange messages and files, never conversation.

Rejected: per-step model variants and agent "modes" switched during the work.

## 2. A step works or routes; a router never judges

Agents, calls, approvals and compositions work. Routing reads only explicit
signals. After an agent, routing is always by the agent's choice, submitted
with the standard `agsdl_submit_result` tool (snake_case, `agsdl_` prefix, no
dots, so that every tool API accepts it). A true/false field in a report is a
disguised decision and is not used for routing.

An approval follows the same rule: the keys of its `next` are the choices
offered to a person, whose comment is passed on with the default message.

Every step routes on one word: an agent's or a person's choice, a join's
outcome, or a call's outcome, `passed` or `failed`, from its exit status or
tool error flag. The condition step, which tested values, was removed:
routing on a finer detail of a result is a judgment, made by an agent or by a
script that exits with `0` or not. Declared outcomes per call, such as one name
per exit status, can be added later with `passed` and `failed` as defaults.

The reliability of a choice comes from the host checking it, not from the
mechanism: a tool is the only mechanism every harness offers. Native
structured output is accepted when it gives the same guarantees.

## 3. The message is carried by the route

A route names its target and, optionally, the message it delivers, with
selections from the previous output. The Prepare step disappears.

The prompt is the mission, and only the document author grants the right to
write one. An agent configured with `instructs` submits `instructions` apart
from its results; they become the next step's prompt. Results stay
information, so content an agent read, such as a web page, never becomes a
mission by accident. An agent step may have a default prompt, used when the
arriving message has none. When some routes to a step bring a prompt and
others do not, the default prompt is required, so that the mission never
depends on where the flow came from; and a route that expects instructions
refuses a submission without them. Instructions never widen rights, never
override the receiver's standing instructions, and follow the step's delivery
mode like any message.

Rejected: marking results as instructions, which would let any result of a
configured agent become a mission; and merging prompts at joins, where
several branches may bring one.

## 4. Automatic correction

The host checks a submitted result at once and returns precise errors to the
agent, which corrects in the same conversation. `maxCorrections` (default 2)
bounds corrections of submissions; `completionCheck.maxFailures` (default 3)
bounds failed checks, which reflect unfinished work rather than a misused
tool. Then the step fails. The hand-drawn correction loops of 0.2 disappear.

## 5. Harness modules, not bindings

AgSDL defines standard agent properties. A harness module, a data file
maintained in this repository, declares for one harness whether each property
is native, approximate or absent, and how each permission is enforced. The
specification, not the module, fixes the severity of each situation. Modules
never change what a property means. One flow can mix harnesses; each agent
uses one.

Rejected: modules in a separate repository; a per-property "best effort"
flag (deferred, and never for permissions or limits).

AgSDL standardizes what harnesses actually do, even when only one harness does
it. It does not invent harness features: an absent feature stays absent.

## 6. Permissions: the document asks, the host grants

Six actions (`read`, `write`, `shell`, `network`, `mcp`, `delegate`), three
effects (`allow`, `ask`, `deny`) and three presets. A document may come from
anyone, so it only requests a ceiling; messages never widen rights; sub-agents
only narrow. Presets act on the agent's zone: its workspace plus the
`directories` it lists. Reading outside the zone is denied unless `outside`
is `read`, which is the default only with `full`, so that a user's secrets are
not readable by default. Paths may be relative, home-relative or absolute.
Between matching rules the most restrictive wins, not the most specific,
because path specificity has no portable definition; whole directories are
added with `directories`. Permissions have no approximate support: a `deny` or `ask` the
harness cannot enforce is an error. Harness rules that only guard the
harness's own tools count for reads, writes and network access only when the
agent has no shell, since `cat` or `curl` would pass them by. `reviewer` says whether a person or a
reviewing model answers `ask` actions, as Codex auto-review and the Claude Code
auto mode do for a whole session; a per-rule effect was rejected because Codex
cannot mix both reviewers in one agent. `permissions` is required: a default
would either hide a forgotten field until run time or, for a restrictive
default, make an agent invalid on harnesses that cannot enforce it.

## 7. Definitions and instances

A definition is configuration; an instance is a running agent. Steps use the
shared instance, a named instance, or a fresh `new` instance per work. Two
steps with the same definition and instance share a conversation: that is how
one mission continues, for example through corrections in a loop.

## 8. Delivery to a working instance

`queue` (default) waits for the current work to end. `steer` joins the current
work when there is one, and otherwise starts its own work. A strict steering
mode that fails when the instance is idle was rejected: it lost messages for
no benefit.

## 9. Joins are deduced from the graph

The origin of a join is its immediate dominator; branches are the paths from
the origin's targets to the join. `after` and `members` disappear. Joins wait
for all started branches, or for a quorum of accepted choices, with outcomes
`done`, `reached` and `missed`. "First acceptable" is a quorum of one; having
no acceptable result is the outcome `missed`, not an error. A route leaving a
branch closes the group; a branch can end without a result, including when its
`steer` message is absorbed.

## 10. Compositions are full flow fragments

The 0.2 restrictions on compositions (no parallel routes, joins, steering or
nesting) came from the old join bookkeeping. They are lifted; nesting is
allowed without cycles.

## 11. How an agent conducts its work

`instructions` carry the method. `plan` gives a work plan visible to the host,
as Codex and Claude Code do natively. `planFirst` keeps the agent read-only
until it presents a plan, which helps small models and lets a person approve
before changes; with `ask` the lock must be enforced. A
`completionCheck` command must succeed before a result is accepted. The host
runs it when the result tool receives a submission, confined to the agent's
permissions, so it does not depend on each harness's stop hooks, which run at
the end of a turn and outside the sandbox. A judgment by another agent stays
in the flow.

Rejected: a document-supplied to-do list (only one harness lets anything but
the model write its plan).

## 12. Values in modules

Modules list values only for closed vocabularies, such as Claude Code's
effort levels. Open values, such as model names, are suggestions for editors;
the host checks them at launch. Effort is closed or open per harness: Codex
accepts any level a model advertises, so its module only suggests levels.
