# Proposal 0005: A2A 1.0 external binding

- Status: proposed
- Date: 2026-09-02
- External specification edition: A2A 1.0.1
- External protocol version: A2A 1.0

## Problem

A2A describes how a client discovers and interacts with an opaque remote agent
server. AgSDL aims to describe the internal and external structure of a complete
agentic system. The two models overlap at interfaces, messages, runtime work,
security declarations, and outputs, but their boundaries are different.

A direct field-by-field import would create false equivalences. An A2A Agent
Card does not expose an internal system graph. An A2A AgentSkill is advertised
service metadata, not an AgSDL Skill. An A2A Task is runtime data, not an AgSDL
Control flow. An A2A Artifact can be updated while AgSDL reserves immutable
artifact identity for sealed content.

AgSDL needs an external binding specification that can reference A2A precisely,
preserve these differences, and state what evidence supports each claim. The
binding specification must not copy the A2A wire model or claim interoperability
from structural metadata.

## Scope

This proposal defines candidate semantics for:

- referencing a public or authenticated extended Agent Card;
- recording A2A specification and protocol versions;
- selecting one advertised AgentInterface as a resolved binding;
- relating advertised AgentSkills to AgSDL definitions without inference;
- observing Tasks, Messages, Artifacts, streams, and push notifications;
- preserving A2A extension requirements;
- mapping authentication declarations without turning them into authority;
- interpreting terminal and interrupted Task states; and
- attaching bounded structural and runtime evidence.

It does not define AgSDL serialization, an A2A client or server, a generated
Agent Card, an adapter, credential exchange, or a runtime conformance claim.
Proposal acceptance would not make this binding specification normative.
Normative text, schemas, fixtures, and executable mapping tests must follow after
AgSDL selects a serialization.

## External source identity

The binding specification targets the A2A Project release `v1.0.1`, commit
`3303592588e388e62e0f69f701af531d2f4e3991`. That release is the specification
edition. The protocol version declared in AgentInterface and exchanged with a
server is `1.0`. AgentCard `version` identifies the remote server's own version
and remains a separate version domain.

A binding specification version must pin all of the following:

| Item | Required identity for this binding specification |
| --- | --- |
| A2A specification edition | `1.0.1` |
| A2A protocol version | `1.0` |
| A2A source tag | `v1.0.1` |
| A2A source commit | `3303592588e388e62e0f69f701af531d2f4e3991` |
| Authoritative data model | `specification/a2a.proto` at that commit |
| Binding specification identity | A future AgSDL-owned stable identity and version |

The source hashes in `docs/research/a2a-v1.0.1.sha256` are review evidence, not
a replacement for those version identities.

The tagged sources disagree on the HTTP method for SubscribeToTask, the JSON
name shown for AgentCard security requirements, whether an HTTP+JSON stream
closes at an interrupted Task state, and whether `TASK_STATE_AUTH_REQUIRED`
names missing authentication or an in-task authorization request. A resolver
records these as upstream source findings. It uses the proto-derived data-object
name `securityRequirements`. It leaves the affected HTTP+JSON and Task-state
behavior indeterminate unless the binding operation pins an upstream erratum,
declares the external authentication or authorization procedure, or supplies
targeted runtime evidence for the behavior it uses. AgSDL must not publish a
silent correction under the A2A 1.0.1 identity.

## Proposed terms

### A2A external binding specification

An **A2A external binding specification** is a versioned AgSDL-owned definition
of the requirements, mappings, and evidence rules for one external A2A edition.
It is not a conformance profile or a configuration profile. It does not support
a conformance claim by itself. A later proposal must define any relation between
external binding specifications and either AgSDL profile kind.

### A2A external agent binding requirement

An **A2A external agent binding requirement** is a proposed binding-requirement
record that connects one AgSDL boundary to an externally described A2A server
boundary. It identifies the Agent Card reference constraints, A2A version
identities, expected reference kind, resolution and integrity requirements,
required capabilities and extensions, and any explicit portable mapping
constraints. It does not contain a resolved source URI, endpoint, Agent Card
observation, or selected security requirement.

The record may attach to an AgSDL System interface or Agent interface. Its
attachment states which AgSDL boundary is exposed or consumed. It does not
assert that the Agent Card describes the whole attached System or the full
definition of the attached Agent.

Conceptual resolution validates this requirement without selecting an endpoint
or implementation. It never changes the requirement into another record kind.

### A2A resolved external agent binding

An **A2A resolved external agent binding** is a deployment-specific resolved
binding that identifies the A2A external agent binding requirement it satisfies.
It records the selected target and exact AgentInterface, the observed Agent Card
snapshot, validation results, and the target facts needed by the declared
operation. Replacing this resolved binding does not modify the portable
requirement.

### Agent Card observation

An **Agent Card observation** is an immutable artifact that snapshots resolution
evidence for one retrieved public or extended Agent Card. The retrieval event
remains a separate occurrence and refers to the snapshot. The snapshot records:

- retrieval source and time;
- public or extended card kind;
- content digest and, when available, signature-verification result;
- A2A specification edition used for validation;
- declared server version and ordered supported interfaces;
- the fields used by the binding;
- authentication mechanism class without embedding credentials;
- for an extended card, a protected or pseudonymous Principal reference or
  authorization-partition identity, tenant scope, and cache or session scope;
- cache validators when present; and
- validation findings and unknowns.

A later retrieval produces another observation. A resolver must not update an
existing observation in place. A public Agent Card and an authenticated
extended Agent Card remain separate observations. A processor may compare or
compose their declared information only through an operation that reports
field provenance and conflicts.

### A2A mapping assertion

An **A2A mapping assertion** is an author declaration relating one identified
A2A subject to one identified AgSDL subject. It states the relation, direction,
scope, and evidence requirement. Supported candidate relations are:

- `exposes boundary as`, from an AgSDL System or Agent interface to an Agent
  Card observation;
- `binds interface through`, from an AgSDL Interface to a selected A2A
  AgentInterface;
- `advertises as service`, from an AgSDL Interface operation or other future
  externally advertised service definition to an A2A AgentSkill;
- `observes occurrence as`, from an A2A Task, Message, status update, artifact
  update, or push delivery to an AgSDL occurrence or trace record; and
- `seals as`, from a completed A2A Artifact assembly to an AgSDL immutable
  artifact.

Equal names, identifiers, descriptions, tags, examples, media types, endpoints,
or payloads never create a mapping assertion.

A binding requirement may constrain which relations a resolved binding must
record, but those portable constraints do not identify a resolved A2A subject.
The resolved binding records each mapping assertion and its evidence separately.

## Binding record information

The future serialization must keep portable requirements separate from resolved
deployment facts.

An A2A external agent binding requirement preserves:

| Information | Requirement |
| --- | --- |
| Binding specification identity and version | Required |
| A2A protocol version constraint | Required |
| Agent Card reference requirement | Required, expected kind `A2A AgentCard` |
| Resolution mode | Required: offline snapshot, controlled retrieval, or deployment observation |
| Integrity requirement | Required: digest, trusted signature policy, or explicit indeterminate result |
| Attached AgSDL boundary | Required |
| Required A2A capabilities | Explicit, possibly empty |
| Required A2A extensions | Explicit, possibly empty |
| Allowed standard or custom bindings | Explicit |
| Acceptable authentication mappings | Explicit, possibly empty |
| Portable mapping constraints | Explicit, possibly empty |
| Evidence requirements | Required for every claimed mapping or runtime feature |
| Unknown and loss handling | Required |

The binding specification identity pins the A2A specification edition, source
tag, source commit, and authoritative data model. A binding requirement must not
repeat or override those values. This keeps the binding specification as the
single source of external source identity.

An A2A resolved external agent binding preserves:

| Information | Requirement |
| --- | --- |
| Satisfied A2A external agent binding requirement | Required |
| Resolved Agent Card reference and source URI | Required |
| Selected Agent Card observation | Required |
| Selected AgentInterface and array position | Required |
| Endpoint, protocol binding, protocol version, and tenant | Required |
| Target runtime or environment element | Required |
| Validation results and unknowns | Required |
| Selected authentication requirement and transport mapping | Required when the card protects the selected interface |
| Runtime secret references | Required when the selected interface needs credentials |
| Mapping assertions and evidence | Explicit, possibly empty |

Secret values, bearer tokens, push notification credentials, private keys, and
live authentication evidence are prohibited in a definition record. They are
external secret references or protected occurrences.

## Mapping rules

### Agent Card boundary

An Agent Card maps to an external A2A server boundary description. A processor
must not infer any of the following from a card:

- a complete AgSDL System;
- an internal Agent definition or participant count;
- topology or control flow;
- models, prompts, tools, memory, knowledge, or state definitions;
- effective policy, authority grants, or approval rules;
- deployment architecture; or
- runtime conformity with advertised capabilities.

An author who controls both descriptions may assert that a System or Agent
exposes the card. That assertion establishes an intended correspondence, not
runtime evidence.

### Interfaces

An A2A AgentInterface combines endpoint, protocol binding, protocol version,
and optional tenant routing. It maps to a resolved transport or deployment
binding for an AgSDL Interface. It does not alter the portable operation
contract.

A resolver must preserve the card's interface order and select one exact entry.
It records the Agent Card observation digest, array position, endpoint,
protocol binding, version, tenant value, and binding media types. Standard
binding identifiers are `JSONRPC`, `GRPC`, and `HTTP+JSON`. JSON-RPC uses
`application/json`, HTTP+JSON prefers `application/a2a+json`, and HTTP streaming
uses `text/event-stream`. A custom binding identifier must meet the A2A URI and
breaking-version requirements before the binding specification treats it as portable
external identity.

When a card advertises several interfaces, structural validation can confirm
their declarations. Only runtime tests can support A2A's equivalence
requirement across them.

The binding requirement references A2A's application operation set rather than
copying its wire shapes. A mapping declares which AgSDL Interface operations initiate or
observe SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask,
SubscribeToTask, the four push configuration operations, and
GetExtendedAgentCard. Capability-gated operations remain unavailable when the
card does not advertise their capability. Omitting an operation from an AgSDL
mapping means no mapping is claimed. It does not mean the A2A operation ceased
to exist.

### Advertised skills

An A2A AgentSkill maps by default to external advertised service metadata. It
does not map by default to AgSDL Skill, Tool, Interface operation, Role,
Authority grant, or implementation feature.

An `advertises as service` assertion may target an AgSDL Interface operation or
a later core entity for externally advertised services. The assertion must
state how A2A input and output media types correspond to the target contract and
how skill-level security requirements relate to the card-level requirements.
The binding specification must not infer that one set refines, replaces, or combines with the
other.

Because A2A does not invoke a skill identifier, the assertion cannot claim
skill-level dispatch unless an extension or tested implementation behavior
defines it.

### Tasks and long-running work

An A2A Task is an execution occurrence identified in the remote server's task
namespace. It may correlate with an AgSDL execution, protocol instance, control
flow instance, or work item only through an `observes occurrence as` assertion.
It never becomes a reusable definition.

The mapping must keep A2A Task ID, context ID, server identity, selected
interface, and protocol version together. A bare Task ID is insufficient across
servers or tenants.

Polling, streaming, and push notifications are alternative observation
mechanisms. Their availability is a binding capability. None changes the
portable meaning of an AgSDL Control flow or Protocol.

CancelTask is a request against active work. A successful response reports the
Task's resulting state. It does not prove interruption of every internal action,
revocation of credentials, rollback, or compensation of external effects.

### Messages

An A2A Message can supply an AgSDL Message occurrence when an explicit mapping
identifies the relevant AgSDL Interface operation and Principals. A2A role
`ROLE_USER` or `ROLE_AGENT` identifies a protocol side, not a Principal.
Authentication evidence and Principal identity need separate records.

Context ID, Task ID, reference Task IDs, and Message ID remain distinct
correlation values. A processor must not infer causal order from context
membership alone. It must also report that Task history may omit protocol
messages when a claim depends on complete communication evidence.

### Artifacts

An A2A Artifact update is execution data. The processor assembles updates by
Task and Artifact ID under the append and last-chunk rules. The content may map
to an AgSDL immutable artifact only when:

1. the assembly reached its declared completion condition;
2. every required part is present;
3. the processor records a content identity or integrity reference;
4. the immutable record identifies the Task and update evidence from which it
   was derived; and
5. no later update can silently mutate that immutable identity.

A terminal Task state does not repair missing chunks. A last chunk does not by
itself prove that the Task completed successfully.

### Streaming

For a message-only stream, the binding requirement expects exactly one Message and stream
closure. For a task lifecycle stream, it expects an initial Task followed by
zero or more status or artifact updates. The general operation rule requires
closure at a terminal Task state. The HTTP+JSON section also requires closure
at an interrupted state, so an HTTP+JSON binding cannot claim one portable
closure rule without an upstream erratum or targeted runtime evidence.

Each StreamResponse carries exactly one Task, Message, status update, or
artifact update. A canonical 1.0 mapping has no `kind` discriminator and no
TaskStatusUpdateEvent `final` field. A processor classifies either field as
legacy input under a separately declared migration path rather than silently
accepting it as canonical 1.0.

Runtime evidence for streaming must record ordering, reconnect behavior,
terminal and interrupted-state closure, and whether concurrent subscribers
observed equivalent event sequences. A card's `streaming` flag is only an
advertised capability.

### Push notifications

Push configuration is a runtime occurrence scoped to a Task. The callback URL,
configuration ID, token, authentication scheme, credential reference, creation
time, deletion time, and delivery evidence do not belong in the static Agent
Card mapping.

A binding requirement may declare webhook protection, callback trust boundary,
replay handling, delivery verification, and retention needs. A runtime claim
needs tests for payload shape, authentication, task scoping, duplicate or lost
delivery behavior, HTTP 2xx acknowledgement, SSRF-resistant URL validation,
and cleanup. A2A requires at least one delivery attempt and permits duplicates,
retries, and eventual abandonment. It does not define exactly-once or guaranteed
eventual delivery.

### Extensions

The binding requirement records each A2A extension by URI, required flag, and
the AgSDL operation for which support matters. The resolved binding records the
extension parameters used by the selected interface. A required A2A extension
is a required external binding capability for that runtime interaction. It may
motivate a future AgSDL implementation feature, but it does not acquire that
AgSDL identity by being required in A2A.

An unsupported required extension stops the interaction. An unsupported
optional extension may be ignored only within A2A's rules and the declared
AgSDL fallback. A processor must not silently interpret A2A extension metadata
as portable AgSDL meaning.

### Security

Agent Card security schemes and requirements map to AgSDL authentication and
transport binding requirements. They do not map to Authority grants or
permitted Authorization decisions.

The binding requirement identifies acceptable authentication mappings. The
resolved binding identifies:

- the selected A2A security requirement alternative;
- its referenced scheme definitions and scopes;
- the Principal identity expected after authentication;
- where authentication evidence is observed;
- the policy application point that authorizes the requested action;
- the trust boundary crossed by the request; and
- secret references needed by the resolved binding.

Runtime evidence must show authorization on every A2A operation. Task listing,
lookup, cancellation, subscription, and push configuration remain scoped to the
authenticated caller. The authorization check must precede any lookup or
response that could reveal an inaccessible resource's existence.

An Agent Card signature observation records canonicalization edition, key
identity, signature result, trust policy result, verification time, and
freshness or revocation status. Signature success alone does not authenticate a
runtime endpoint or authorize a request.

When `TASK_STATE_AUTH_REQUIRED` represents an in-task authorization request
under A2A section 7.6, credentials remain out of band unless the binding
requirement names an extension for in-band exchange and the resolved binding
selects support for it. The binding requirement declares this use explicitly
because the proto state comment instead says authentication is required. The
definition must never put a credential in a Message example or mapping
parameter.

## Task state mapping

The binding specification classifies A2A Task states without renaming them:

| State | A2A class | Allowed generic mapping |
| --- | --- | --- |
| `TASK_STATE_UNSPECIFIED` | indeterminate | unknown task state |
| `TASK_STATE_SUBMITTED` | active | acknowledged work |
| `TASK_STATE_WORKING` | active | work in progress |
| `TASK_STATE_INPUT_REQUIRED` | interrupted | explicit wait for input |
| `TASK_STATE_AUTH_REQUIRED` | interrupted | explicit wait whose authentication or authorization meaning is declared by the binding |
| `TASK_STATE_COMPLETED` | terminal | successful A2A task termination |
| `TASK_STATE_FAILED` | terminal | failed A2A task termination |
| `TASK_STATE_CANCELED` | terminal | canceled A2A task termination |
| `TASK_STATE_REJECTED` | terminal | rejected A2A task termination |

Interrupted states are nonterminal even though blocking SendMessage may return
on them. A terminal A2A Task maps to an AgSDL Protocol, Control flow, or System
terminal only when a mapping assertion enumerates that state and runtime tests
exercise the mapped outcome. Cancellation does not prove compensation or
absence of effects. Rejection does not identify which policy or actor refused
the work.

## Validation and evidence

The binding specification defines four separate coverage classes.

### Source identity

The verifier confirms the content identity of the three pinned specification
files against recorded hashes. `scripts/verify-a2a-1.0.1-sources.sh` implements
this check for a local upstream source tree. The research record separately
identifies the release tag and commit from which those files were obtained.
Passing the script does not prove Git provenance, an Agent Card, or runtime
behavior.

### Binding structure

After AgSDL selects a serialization, fixtures must cover:

- the binding specification identity and its pinned A2A source identity;
- the A2A protocol version constraint;
- expected Agent Card reference kind;
- controlled resolution and snapshot identity;
- exact AgentInterface selection;
- explicit required capability and extension sets;
- distinct public and extended card observations;
- protected audience, tenant, and cache scope for extended card observations;
- mapping target kinds;
- prohibited secret material; and
- unknown, required, optional, and loss behavior.

Until those fixtures and a validator exist, no processor can claim support for
this binding specification.

### Mapping behavior

Executable adapter tests must cover every claimed mapping relation. They must
include negative cases for AgentSkill-to-Skill inference, protocol-role-to-
Principal inference, incomplete Artifact assembly, interrupted-state terminal
mapping, missing messages in history, and authentication-to-authorization
collapse.

### A2A runtime behavior

Runtime evidence must identify the A2A test suite repository and commit, system
under test, Agent Card digest, selected interfaces, capabilities, extensions,
security configuration class, protected audience or authorization partition for
an extended card, tests run, skipped tests, findings, and report digest. Each
advertised interface needs coverage. Capability tests apply only when the card
advertises the capability.

The official A2A TCK is the preferred upstream suite. Its current 1.0 tags are
alpha releases, so a report must retain that maturity label and cannot be
presented as stable complete A2A 1.0.1 certification. AgSDL mapping tests remain
separate because the TCK does not inspect the internal AgSDL description.

## Candidate binding requirements

These identifiers are local to this proposal.

- **A2A-BIND-001 Source identity.** A binding requirement identifies the binding
  specification identity and version. That identity pins the A2A specification
  edition, source tag, source commit, and authoritative data model. The binding
  requirement separately constrains the A2A protocol version. A resolved 1.0
  client binding sends the A2A-Version service parameter explicitly because
  omission selects the 0.3 compatibility behavior.
- **A2A-BIND-002 External boundary.** A binding requirement treats the Agent
  Card as an external boundary description and creates no internal System or
  Agent facts by inference.
- **A2A-BIND-003 Controlled reference.** The binding requirement declares the
  expected Agent Card kind, resolver mode, and integrity requirement. The
  resolved binding records the resolved reference and observed snapshot. An
  extended card observation also identifies its protected audience or
  authorization partition, tenant scope, and cache or session scope.
- **A2A-BIND-004 Interface selection.** An A2A resolved external agent binding
  identifies its satisfied requirement and selects one exact
  AgentInterface and preserves endpoint, binding, version, tenant, order, and
  declared mappings to the A2A application operation set.
- **A2A-BIND-005 Advertised service distinction.** AgentSkills remain external
  advertised service metadata unless explicit mapping assertions relate them
  to AgSDL definitions.
- **A2A-BIND-006 Occurrence identity.** Tasks, Messages, updates, push
  configurations, and deliveries remain runtime occurrences with server,
  tenant, and correlation scope.
- **A2A-BIND-007 Artifact sealing.** Mutable A2A Artifact assembly becomes an
  immutable artifact only after completion and content identity checks.
- **A2A-BIND-008 State classification.** Interrupted and terminal A2A states
  retain their exact classifications. Cross-model terminal mappings are
  explicit and tested.
- **A2A-BIND-009 Extension handling.** Required A2A extensions fail closed and
  optional extension fallback remains explicit for the AgSDL operation.
- **A2A-BIND-010 Security separation.** Authentication schemes, authentication
  evidence, secret references, authority, authorization, and Agent Card
  signature trust remain distinct.
- **A2A-BIND-011 Evidence scope.** Every conformance claim identifies source,
  structural, mapping, and runtime coverage separately and reports unknown or
  untested portions.
- **A2A-BIND-012 No untested equivalence.** Multiple advertised A2A interfaces
  are not called equivalent without runtime evidence across each interface.
- **A2A-BIND-013 Upstream conflicts.** A processor reports conflicts within the
  pinned A2A sources and does not silently choose behavior for an affected
  binding operation.

## Consequences

The binding specification can describe an A2A dependency or exposure without importing the
A2A wire model into AgSDL. It lets processors preserve exact external
identities while keeping AgSDL's internal model richer and independent.

The cost is explicit evidence and mapping records. An Agent Card alone produces
few internal AgSDL facts. That is intentional. The remote system is opaque, and
inventing its graph would make later inspection or migration unreliable.

No schema is added by this proposal. AgSDL has not selected a serialization,
and a schema cannot create the semantics above. The first implementation step
after syntax selection should be a binding schema plus positive and negative
fixtures for A2A-BIND-001 through A2A-BIND-013.

## Alternatives considered

### Import Agent Card as an Agent

This is concise but asserts that the card describes one internal participant.
A2A makes no such guarantee and deliberately preserves server opacity.

### Import AgentSkill as Skill

The shared name hides incompatible contracts. AgentSkill is discovery metadata
and has no direct invocation method. AgSDL Skill composes reusable internal
behavior.

### Treat Task as Control flow

A Task reports runtime work and status. It does not define internal steps,
branch conditions, participant roles, or transitions.

### Copy A2A data objects into AgSDL

Copying would create a second, drifting source for the wire model. Versioned
external references and explicit mappings retain A2A ownership of its protocol.

### Use a TCK pass as the entire binding claim

The TCK exercises an A2A server. It cannot prove that an AgSDL document maps the
server correctly or describes its internal graph. Its current 1.0 releases are
also alpha.

## Security considerations

Agent Cards and their linked endpoints are untrusted external inputs until
policy accepts their source, integrity, and freshness. Controlled resolution
must limit schemes, hosts, redirects, response sizes, and network locations.
Extended cards add an authenticated retrieval boundary and may reveal metadata
not present in the public card.

Interface URLs, tenant values, extension parameters, metadata, file references,
webhook URLs, and signature key locations can all redirect a processor or
runtime across trust boundaries. Structural validity never authorizes network
retrieval or execution.

Push notification registration creates an inbound endpoint and a credential
handling path. Deployments need callback authentication, replay defenses,
task-scoped tokens, URL validation, delivery reconciliation, and cleanup.

Task cancellation and failure do not prove that external effects stopped or
were compensated. An AgSDL safety claim needs effect evidence from the
responsible runtime and external services.

## Compatibility impact

AgSDL 0.0.1 has no normative syntax, external binding specification, or
interoperability promise. This proposal breaks no conforming document. It
narrows future design by reserving explicit distinctions that a serialization
and adapter must preserve.

The binding specification targets A2A protocol version 1.0 and specification
edition 1.0.1. A2A 0.3 uses different object shapes and cannot be accepted by
silently changing the version field. Canonical v1 uses `CANCELED`, omits the
former HTTP+JSON `/v1` path prefix, and has no `kind` or TaskStatusUpdateEvent
`final` fields. A future 0.3 binding specification or migration adapter needs
separate fixtures and loss reporting.

## Unresolved questions

1. What final core term should name externally advertised service metadata?
2. Should the A2A external agent binding requirement attach only to Interface
   definitions, or also directly to System and Agent boundaries through a
   concise form?
3. Which Agent Card fields must an offline package snapshot include for
   reproducible resolution, and which may remain external links?
4. What evidence is sufficient to relate an A2A Artifact's last chunk to an
   immutable AgSDL artifact when the Task has not yet terminated?
5. How should an adapter report equivalent functionality across interfaces when
   the upstream TCK lacks a stable release for the targeted A2A edition?
6. Should an authenticated extended Agent Card be allowed to remove public
   declarations, or only add and refine them, in an AgSDL composition result?
7. Which A2A extension URIs, if any, should receive separately maintained AgSDL
   binding specifications?
8. Which future A2A erratum or release should close the HTTP+JSON
   SubscribeToTask method conflict, and what compatibility relation should
   AgSDL publish for existing 1.0.1 implementations on each method?
9. Should the same erratum resolve whether HTTP+JSON streams close at
   interrupted states, or should AgSDL treat closure as a separately tested
   binding behavior for all A2A 1.0.1 evidence?
10. Should AgSDL require an extension identity to distinguish authentication
    from in-task authorization uses of `TASK_STATE_AUTH_REQUIRED`, or is an
    explicit external procedure sufficient?
